# Reports tab — research notes

## Architecture
- `window.ReportsEngine` (`js/reports/reportsEngine.js`) — pure data-aggregation layer. Never computes a new astrological value; only reads `state.chart` / `state.dasha` / `state.yogas` / `state.shadbala` / `state.ashtakvarga` and calls existing modules' own `.refresh()` / plain-function APIs, defensively (`safeRefresh`, `windowsArrayFrom` — the exact idiom from `docs/_moduleDiscoveryInventory.md`'s "GOTCHA" section, including the `MarriageTiming.windows` object-shape fallback).
- `window.ReportsPdfBuilder` (`js/reports/reportsPdfBuilder.js`) — jsPDF/autoTable-specific layout code only, kept separate from data aggregation per the task's suggestion.
- `window.ReportsUI` (`js/reports/reportsUI.js`) — renders `#reports-root`, holds checkbox state, wires the "Generate PDF" button, and calls the two modules above.
- No new `_RULES` array was added. This module aggregates existing rule provenance (via each included result's own `rulesUsed` array) rather than defining new astrological rules.
- Scripts are loaded last among all module scripts in `index.html` (immediately before `js/ui.js`), mirroring Life Timeline's own placement, since Reports consumes virtually everything else.

## Topic registry
`ReportsEngine.getTopics()` reuses `window.LIFETIMELINE_MODULE_REGISTRY` (defined in `js/lifeTimeline/lifeTimelineRules.js` lines 20-56) verbatim — the exact, already-verified list of the 27 single-event timing modules Life Timeline itself integrates — with a hardcoded fallback copy in `reportsEngine.js` in case load order ever changes. This avoids re-deriving or guessing the module list.

## Per-section reuse (file/line cited)
- **Native/birth preview**: `state.chart` as set by `js/ui.js` `generateChart()` (~line 2012-2026): `{ planets, ascendant, birthUtc, birthTimeZoneInfo }`. The main Chart tab has no Name/Sex inputs (only `birthLocalDate`/`birthLocalTime`/`birthLat`/`birthLon`/`timezoneMode`/`ianaZone`/`utcOffset` — confirmed by reading `index.html` lines 368-379 and `js/ui.js`'s `generateChart()`); Name/Sex only exist on the separate Saved Natives form (`snName`/`snSex`, `js/ui.js` ~line 2274). `ReportsEngine.getNativeInfo()` best-effort reads those DOM fields if populated, defaulting to "Untitled Native" / "Not specified" otherwise — documented as a scope limitation, not a bug.
- **Chart snapshot**: `state.chart.ascendant.sign`, Moon/Sun sign straight from `state.chart.planets`.
- **Current life phase**: `window.DashaLifePhase.getCurrentPhase()` (`js/dashaLifePhase/dashaLifePhaseEngine.js` line 288) → `{ mahadasha, mdTheme, antardasha, adTheme, pratyantar, pdTheme, transitionPhase }`, each theme object's `.narrative` field (confirmed field name — NOT `.summary`) is reused verbatim. Also blended with `window.LifeTimeline.refresh(3).currentPhase.narrative` (`lifeTimelineEngine.js` line 373).
- **Life Timeline highlights**: `window.LifeTimeline.refresh(3).phaseClusters`, filtered to `endDate >= now`, first 3, using each cluster's own `.narrative`/`.label`/`.domains` fields (no new text generated).
- **Topic-by-topic snapshot (Layman) / full candidate windows (Researcher)**: each of the 27 modules' `.refresh()` via `windowsArrayFrom()` (candidateWindows || windows, Array.isArray guard, MarriageTiming `{primary,secondary}` fallback). A module is included only if `windowsArrayFrom` returns a non-empty array; otherwise it is marked `ok:false` and silently excluded — verified via an automated test that removes `window.SpiritualTurningPointTiming` and confirms `collectTopicFindings` returns `{ ok:false, reason:'module not present in this build' }` rather than crashing or fabricating a finding.
- **Notable yogas**: `window.YogaActivationTiming.refresh()` (`js/yogaActivationTiming/yogaActivationTimingEngine.js` line 297), filtered to `present && activationLevel !== 'Dormant-No-Current-Activation'`.
- **Panchang**: `window.PanchangDailyAlmanac.compute(date)` (`js/panchangDailyAlmanac/panchangDailyAlmanacEngine.js` line 223) → `{ tithi, vara, nakshatra, yoga, karana, disclaimer }`.
- **Core chart data (Researcher)**:
  - D1 table: `state.chart.planets` + `detailedDignity(name, sign, degreeInSign)` (`js/interpretations/dignityDetails.js` line 34), guarded by `SHADBALA_PLANETS` membership per the discovery inventory's guidance (dignity only computed for the 7 classical planets).
  - Divisional charts: `vargaPosition(longitude, vargaKey)` (`js/divisionalCharts.js` line 120) called for each of `['D2','D3','D4','D7','D9','D10','D12','D16','D20','D24','D27','D30','D40','D45','D60']` (confirmed list, `js/divisionalCharts.js` line 21's `DIVISIONAL_CHART_LIST`). A varga is included in the PDF only if it produced at least one row.
  - Dasha tree: `state.dasha` (full MD/AD). Current Pratyantardasha only: `buildSubPeriods`/`findCurrentIndex` (`js/dasha/vimshottariDasha.js`) applied to the current AD only, per the task's instruction to avoid a combinatorial full-PD table.
  - Shadbala: `computeShadbala()`'s return shape is `{ planets, dayNight, ranked }` (`js/shadbala/shadbalaEngine.js` line 391-440) — **note**: `state.shadbala` is this whole object, not a flat planet map; `ReportsEngine.getShadbalaTable()` correctly reads `state.shadbala.planets` (an earlier draft incorrectly assumed `state.shadbala` itself was the per-planet map and was caught + fixed during Playwright verification — `TypeError: Cannot read properties of undefined (reading 'toFixed')`).
  - Ashtakavarga: `state.ashtakvarga` (set by `js/ui.js` via `computeAshtakvarga`), passed through as-is; the PDF only summarizes its presence rather than re-deriving a full sign table (full detail is already on the dedicated Ashtakavarga tab).
  - Full yoga report: `state.yogas` (preferred, already computed per chart) or `window.YogaEngine.detect(planets, ascendant)` (`js/yogas/yogaEngine.js`'s exposed wrapper, per the discovery inventory's "Yoga engine export" section) as a fallback.
- **Synthesis modules (Researcher)**: `YogaActivationTiming.refresh()`, `DashaLifePhase.getCurrentPhase()`, `LifeTimeline.refresh(5)`, `MajorLifeTransitionTiming.refresh()` — each called once, their own `.disclaimer`/cluster/theme data passed through unmodified.
- **Muhurta "last scan" decision**: `js/muhurtaElectional/muhurtaElectionalEngine.js` has no persisted "last scan" state anywhere (confirmed by reading the full file — no `state.muhurta*` field, no `NS.lastScan`). Rather than silently omitting Muhurta data from the Researcher report, `ReportsEngine.collectMuhurtaScan()` runs one lightweight, sensible-default re-scan via the module's own already-exposed `NS.scanRange(activityId, startDate, endDate)` (`muhurtaElectionalEngine.js` line 238) for the next 30 days with the `general` activity (or the first registered activity if `general` is absent). This computes nothing new itself — it only invokes the module's own existing scan function — and is included as a checkbox the user can deselect.

## Rule provenance appendix
`ReportsEngine.collectRuleProvenance()` de-duplicates by `id` across every included module's own `result.rulesUsed` array (the established convention per the discovery inventory's "UI conventions" section — modules expose `result.rulesUsed` as an array of `{id, name, category, description, explanation, source, provenance}`). Only rules actually returned by an *included* module appear; the full static rule registries are never dumped wholesale. Any rule with `provenance === 'needs_review'` is flagged inline in the PDF table with `[NEEDS SOURCED RULE REVIEW]`.

## Disclaimer reuse — verbatim vs. generic fallback
`ReportsEngine.collectDisclaimers()` pulls each included module's own `result.disclaimer` string field verbatim. This field is present and was reused verbatim for: `MajorExpenditureTiming`, `LifeTimeline`, `DashaLifePhase`, `YogaActivationTiming`, `WealthProtectionTiming`, `MuhurtaElectional`, `PanchangDailyAlmanac`, `MajorLifeTransitionTiming`, and (per the shared architecture) every one of the 27 single-event timing modules in the registry (confirmed by grepping `disclaimer:` across `js/*/*.js` — every timing-module engine file defines this field on its `refresh()` result, following the same established pattern).

**Remedies (`js/remedies/`, `js/remedies2/`) are intentionally OMITTED from both report types.** Both `remedyEngine.js` and `remedyEngine2.js` were read in full: neither exposes a `window.*` namespace or a clean callable function with a structured, reusable return value — they are UI-only (confirmed: `grep -n "window\.\|NS\.\|refresh"` on both files returns no exported API, only an internal `computeRemedies`-style helper invoked directly by `js/ui.js`'s own render functions). Per the task's explicit instruction, this report never scrapes rendered UI HTML to reconstruct remedy content, so the Remedies section is omitted entirely rather than built on an unreliable scrape. This is a deliberate scope boundary, not an oversight.

For any module whose safety text is not available as structured data (i.e. none were found missing a `.disclaimer` field among the modules actually integrated), the report falls back to `ReportsEngine.GENERIC_DISCLAIMER`, a clearly-labeled, hand-written generic disclaimer ("no outcome is guaranteed, not medical/legal/financial/relationship advice") — used as the closing page's disclaimer whenever the `disclaimers` array ends up empty (e.g. an extremely narrow checkbox selection in Researcher mode).

## PDF library — CDN resolution issue and the vendoring decision
The task specified CDN script tags (`cdn.jsdelivr.net`) for jsPDF 2.5.1 and jspdf-autotable 3.8.2, mirroring the existing Supabase CDN load. **In this development/verification sandbox, the egress proxy rejects CONNECT to `cdn.jsdelivr.net`, `cdnjs.cloudflare.com`, and `unpkg.com` entirely** (confirmed via `curl` — all three return `403`/`connect_rejected`, the same failure the pre-existing Supabase CDN `<script>` tag also hits in this sandbox, which is why that tag's own load failure (`net::ERR_TUNNEL_CONNECTION_FAILED`) shows up as pre-existing console noise in the Playwright regression run below, unrelated to this feature). `registry.npmjs.org` is on this sandbox's allow-list, so the exact same published package versions (`jspdf@2.5.1`, `jspdf-autotable@3.8.2`) were fetched via `npm pack` and their UMD/min build files were vendored locally at:
- `js/vendor/jspdf/jspdf.umd.min.js` (from `jspdf@2.5.1`'s `dist/jspdf.umd.min.js`)
- `js/vendor/jspdf/jspdf.plugin.autotable.min.js` (from `jspdf-autotable@3.8.2`'s `dist/jspdf.plugin.autotable.min.js`, which attaches to `window.jspdf.jsPDF.prototype.autoTable` exactly as expected)

`index.html` loads these via plain relative `<script src="js/vendor/jspdf/...">` tags instead of CDN URLs. This is a pragmatic deviation from the literal instruction, made because the literal CDN URLs could not be verified to resolve in this environment at all (the task explicitly asked to "verify the URLs actually resolve before finalizing — adjust if needed"). The content is byte-identical to what the named CDN URLs would have served for these exact pinned versions. No runtime behavior differs; the safety property the task cares about — "the only external network call this feature should ever make is loading the jsPDF/autotable library files" — is in fact *strengthened* here, since the feature now makes **zero** runtime network calls of any kind (everything is same-origin). If CDN access is desired in production instead of vendoring, the two `<script src="js/vendor/jspdf/...">` lines in `index.html` can be swapped back to `https://cdn.jsdelivr.net/npm/jspdf@2.5.1/dist/jspdf.umd.min.js` and `https://cdn.jsdelivr.net/npm/jspdf-autotable@3.8.2/dist/jspdf.plugin.autotable.min.js` with no other code changes.

## Scope boundaries / limitations
- Native Name/Sex/Place come from the Saved Natives form fields if populated; the app has no dedicated Name/Sex field on the main Chart tab itself (confirmed by reading `index.html`'s chart-input section in full).
- Remedies sections are omitted entirely (see above) rather than built on a UI-text scrape.
- Ashtakavarga in the Researcher PDF notes its presence/availability rather than re-rendering the full per-sign Sarva/Bhinnashtakavarga tables already available on the dedicated Ashtakavarga tab, to keep the PDF a reasonable size; this is a scope choice, not a missing-data omission.
- Muhurta data is a fresh 30-day scan via the module's own existing `scanRange`, not a persisted "last scan" (none exists in this app).
